## What This Project Teaches

This project trains the full software development lifecycle as a fast, repeatable habit rather than a one-time exercise, and trains client presentation and interview composure more heavily than any other project in the library. A resource has already run one full lifecycle in Project 1 on a single domain they chose and understood. This project forces seven lifecycles, back to back, on domains they do not already know, with an AI coding agent handling the mockup implementation so the resource's attention stays on requirements analysis, feasibility and cost judgment, system and database design, and client-facing presentation.

The deliverable is a working mockup, not a production system: every screen and flow genuinely works when clicked through, but there is no requirement for a real automated test suite, CI/CD, production deployment infrastructure, or a live hosted URL. Each mockup is a standalone file that opens directly in a browser, and each engagement's written record is a single compiled document (`compilation.md`) rather than a scattered set of files, with diagrams drawn as Mermaid directly inside it. This is a deliberate scope cut. It exists so the resource's limited time goes into the parts that are hardest to fake and hardest to teach: correctly scoping an unfamiliar domain, designing soundly under time pressure, and presenting confidently and clearly, especially for resources whose spoken English or interview composure has been flagged as a gap. It is the deliberate repetition of Scoping and Requirements, Development Lifecycle, and Technical Explanation that the flexibility principle in `TSS_Project_Library_Proposal_v2.md` calls out as needing more than a single pass, and it closes with a real, external portfolio and resume outcome rather than only an internal review.

## Assessment Criteria

On successful completion, a resource should show:
- Consistent, improving speed and quality across the seven engagements, visible in the cross-engagement reflection.
- A feasibility note per engagement with a defended, non-placeholder cost estimate.
- Requirements analysis that surfaces at least one unstated domain rule per engagement, not just what the brief states outright.
- Evidence of directing an AI coding agent rather than accepting its first output uncritically (the agent direction log inside each `compilation.md`).
- A genuinely clickable, standalone mockup per engagement, opening with nothing more than a browser, not a static set of screens and not something requiring a live hosted URL.
- A clean five-minute live presentation of problem, solution, and implementation on at least two mentor-selected engagements, with client-style Q&A answered without notes.
- Seven public, demo-ready folders, each holding one `compilation.md` and one mockup, plus a portfolio page and resume and LinkedIn material drawn from this project.

Cost-Aware Design and Business and ROI Fluency default to Mid tier in the map; this project is one of the few places they get direct, repeated practice rather than a single pass. Portfolio Projects and Resume, LinkedIn, and Upwork Readiness default to Junior in the map and are trained here as a concrete deliverable (Phase 4) rather than only the parallel Definition of Done line other projects use.

## Definition of Done

- [ ] Each engagement's mockup is genuinely clickable through its core flow, opening with nothing more than a browser, no live hosting involved
- [ ] Each engagement's `compilation.md` is understandable by a stranger opening it cold on GitHub in under two minutes, with diagrams rendering as Mermaid
- [ ] Presentation checkpoint completed for this tier, across all seven engagements, with two selected and defended live
- [ ] Portfolio Packaging phase completed: public repos, portfolio page, resume and LinkedIn material
- [ ] Assessment criteria checked against actual performance

## Showcase

Each engagement is demoed individually, in under five minutes, in the shape of problem, solution, implementation. The mentor selects two of the seven to walk through live on the review call; the remaining five are covered in writing and video in `PRESENTATION.md`. The mentor should push back on at least one cost estimate and one design decision during the live call to test whether the resource can defend their reasoning under real questioning, mirroring a client conversation rather than a scripted demo. The mentor should also ask the resource to walk through their portfolio page cold, as if deciding whether to hire them, since that is the real-world use this project is built for.

## Depth of Learning

Depth over the seven engagements is deliberately uneven by design: each individual engagement is compressed to roughly one working day, so the artifacts are real but not exhaustive, and the mockup trades production rigor for speed and polish. What is expected to be deep is the habit itself: arriving at each new domain, scoping it correctly, producing the standard deliverable set without hesitation, and presenting it cleanly, sharper each time across the seven. A resource who produces seven shallow, templated engagements has not passed; a resource who produces seven engagements where the domain reasoning and the presentation are visibly sharper each time has, even if none of the seven would survive real production traffic.

## Intended Use Case

Bridges the gap between Project 5 (The Debug Files, diagnosing unfamiliar code) and the Mid-tier build projects (The Knowledge Keeper, The Operator, The Pipeline). Solves three problems at once: it gives fundamental SDLC and client-communication skills a second deliberate repetition on fresh, unfamiliar problems, it exposes a resource to multiple industry domains early, which the twelve-category map does not otherwise test for, and it produces a real, external portfolio and resume outcome the resource can point an interviewer or client to. This last part matters most for resources from non-English-speaking backgrounds, where spoken presentation and interview composure, not technical capability, are usually the actual placement blocker. Useful both as a standard step in sequence and as a targeted assignment for a resource who cleared Project 1 competently but has only ever reasoned about one domain or has not yet built a demonstrable portfolio.
